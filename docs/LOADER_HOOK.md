# D_NAMES 로더 훅 — 동작 확인, 그러나 놓을 자리가 없다

기준일: 2026-08-23  
상태: **훅 기구는 실기 검증 완료 / 목적지 RAM이 게임 스크래치 힙이라 이 설계로는 못 쓴다**

## 1. 만든 것

`tools/patch_map_hook.py` — MAP 오버레이에 트램폴린+스텁을 넣어 `DAT/D_NAMES.BIN`을 별도 적재하고
베이스 표를 그리로 돌린다.

- 로더 규약 확정: `0x800C3158(a0=파일 인덱스, a1=목적지)` 전체 파일 **동기** 읽기.
  내부는 `CdControl(SetLoc)` → `CdRead` → `CdReadSync` + 실패 시 재시도 루프다.
- 파일 인덱스: EXE 경로 표 `0x800E0410`에서 **D_NAMES = 11**, STAYDAT = 28.
- 훅 지점: STAYDAT 로더 래퍼 `0x801547CC`(9워드, 호출자 1곳). 트램폴린 `j 0x8015FAB4`,
  스텁 13워드를 MAP 해제물의 정적 참조 0건 0-run(`0x8015FAB4`, 330 B)에 배치.
- 안전장치는 BATTLE 접근자 패치와 동일(capstone 역디코드 대조, load-delay 검사,
  Expected Write 3건, `j` 영역 검사, 재압축 왕복).

## 2. 훅은 동작한다 (실기)

로더 진입점에 exec BP를 걸어 부팅부터 추적하니 호출 순서가 이렇게 찍힌다.

| # | a0(인덱스) | a1(목적지) | 호출자 |
|---|---:|---|---|
| 1 | 0 (MAP.LZB) | 스크래치 | EXE `0x800C161C` |
| 2 | **28** (STAYDAT) | `0x80020000` | **스텁 `0x8015FAC8`** |
| 3 | **11** (D_NAMES) | `0x80168000` | **스텁 `0x8015FAD8`** |

스텁 종료 지점(`0x8015FAD8`)에 `pause_on_hit` BP를 걸고 **정지 상태에서** RAM을 읽으니
`0x80168000`에 D_NAMES 헤더(`48 00 00 00 5A 34 00 00 1A 5F 00 00 …`)가 그대로 있다.
**추가 CD 읽기, 목적지 지정, 동기 완료가 모두 정상 동작한다.**

> 함정: `tap`/`run_frames`는 frozen 상태를 **자동 resume** 한다. BP로 멈춘 순간의 메모리를 보려면
> `poll_events`와 `read_memory`만 써야 한다. 이걸 몰라 "적재 실패"로 두 번 오판했다.

## 3. 그런데 두 가지가 막는다

### (a) 훅 지점이 너무 늦다

`0x801547CC`는 **스테이지 진입용** 로더다. 그보다 먼저 나오는 **주인공 설정 화면**이 이미
D_NAMES를 읽는다. 베이스만 새 주소로 돌리고 적재가 아직 안 된 상태에서 그 화면이 뜨면
쓰레기를 읽어 `0x25086FE0`으로 점프, RI 예외로 죽는다(관측된 크래시가 정확히 이것).

이분 실험으로 확정했다.
- 스텁만(적재 호출 없음, 베이스 유지) → **정상**
- 스텁 + D_NAMES 적재(베이스 유지) → **정상**
- 스텁 + 적재 + 베이스 재지정 → **설정 화면에서 크래시**

즉 훅은 EXE 쪽(오버레이 적재 직후)으로 옮겨야 한다.

### (b) 목적지가 게임의 스크래치 힙이다 — 이게 진짜 벽

`0x80168000`에 적재된 D_NAMES는 곧 0으로 지워진다. 범인을 잡으니 MAP 초기화의 클리어 루프였다.

```mips
80108D50  lui  $v1, 0x800c ; lw $v1, 0x514($v1)   ; 시작 주소
80108D58  lui  $v0, 0x800c ; lw $v0, 0x518($v0)   ; 길이(바이트)
80108D64  srl  $v0, $v0, 2
80108D70  sw   $zero, ($v1)                        ; 워드 단위로 전부 0
80108D74  addiu $v0, $v0, -1
80108D78  bnez $v0, 0x80108d70
80108D7C  addiu $v1, $v1, 4
```

런타임 값: `*(0x800C0514) = 0x80161508`, `*(0x800C0518) = 0x0004BC28` (310,312 B).
즉 **`0x80161508`–`0x801AD12F` 전체가 게임의 작업 힙**이고 MAP 초기화마다 통째로 0이 된다.
시작 주소는 MAP 이미지 끝과 정확히 같고(`0x80106380 + 0x5B188`), EXE가 오버레이를 적재하는
목적지(`0x800C0514`)와 같은 전역이다 — 압축 오버레이를 힙 앞에 읽어 앞쪽으로 푸는 구조다.
두 번째 쌍 `*(0x800C051C)=0x80165290`, `*(0x800C0520)=0x000415E8`도 같은 영역을 덮는다.

**따라서 "오버레이 위 144 KiB가 비어 있다"던 앞선 판정은 표본 오류다.** 그때는 스테이지 단계만
봤고, 그 단계에서 힙 상단이 마침 조용했을 뿐이다. 힙은 MAP 초기화 때 전부 지워진다.

## 4. 남은 선택지

**(A) 힙을 줄이고 그 꼬리를 쓴다.** `0x800C0518`(과 `0x800C0520`)을 줄이면 클리어 루프가
우리 영역을 건드리지 않는다. EXE는 비압축이라 워드 하나 고치는 일이다. 다만 힙 상단을 게임이
실제로 쓰는지 증명해야 한다 — 클리어 루프가 전 영역을 훑기 때문에 쓰기 관측만으로는 못 가른다.
먼저 줄인 뒤 그 영역에 쓰기 BP를 걸어 한 스테이지+전투를 돌려 확인하는 순서가 된다.
가장 큰 압축 오버레이가 `BATTLE.LZB` 195,867 B이므로 힙 앞쪽 196 KB는 반드시 필요하다.

**(B) 엔진을 건드리지 않고 D_NAMES를 현재 슬롯(53,248 B)에 맞춘다.** 투영 64,349 B 대비
약 **-17%** 압축이 필요하다. 도너가 같은 문제를 `width_compaction`·`despace_nospace`로 풀었고,
이름은 어차피 고정폭 칸에 들어가야 한다. 훅도, 힙 축소도, 베이스 재지정도 필요 없다.

투영 64,349 B는 아직 **모델값**이다(span 배율 1.28–1.39, 이름 1.575). 실제 한국어 D_NAMES
원장을 만들면 확정된다. 그 숫자가 53,248 B 아래면 (B)로 끝나고, 넘으면 (A)를 연다.
