# M_BANKS 단계 기반 조사 (2026-08-23)

## 공간 정책 — D_NAMES와 다르다

소비자 시그니처가 **디스크 스트리밍**을 가리킨다(전부 실측 재확인, 10/10 일치):

| MAP 해제물 | RAM | word | 의미 |
|---|---|---|---|
| `0x4DB34` | | `34040012` | 파일 인덱스 18 |
| `0x4DB48` | | `340700F4` | 상단 헤더 0xF4(61*4) 읽기 |
| `0x4DC30` | | `34070200` | 뱅크당 포인터표 0x200 읽기 |
| `0x4DD58` | `0x801540D8` | `34070400` | 메시지당 런타임 창 0x400 |

493 KB를 통째로 RAM에 올리지 않는다. 따라서 제약은 파일 크기가 아니라:
1. 뱅크 상대 `u16` — 레코드는 자기 뱅크 64 KiB 안에서 주소지정
2. 레코드는 포인터에서 시작하는 **0x400 창 안에서 종단**
3. 헤더 61칸 중 **56칸 사용 / 5칸 여유**

RAM 델타: MAP 해제물 offset + `0x80106380` = RAM 주소 (`0x4E4A8` ↔ `0x80154828` 기준).

## 규모

```
런타임 슬롯 14,336 -> 포인터 대상 12,065 -> 정본 레코드 9,109
정본 레코드 447,728 B = 파일의 90.8%
일본어 포함 9,070 레코드 / 일본어 277,946자
길이 중앙 34 B / p95 132 B / 최대 1024 B
```

**함정: 레코드 길이를 단순 합산하면 1,096,110 B로 파일 크기(493,209 B)를 넘는다.**
포인터 2,798개가 다른 레코드의 접미사를 가리켜 겹쳐 읽히기 때문이다(D_NAMES 내부 앵커 13개와
같은 구조가 대규모로). 물량 산정은 반드시 **종단을 공유하는 것끼리 묶어 정본 하나만** 센다.

## 도구 판정 — Redux가 필요한 이유

- **emucap Mednafen은 이 호스트에서 헤드리스 전용이다.** 검증된 구성이
  `SDL_VIDEODRIVER=dummy` + `-video.driver softfb`라 창이 없다(`scratchpad/run_mf.sh`).
  메모리·BP는 되지만 **사람이 플레이하며 커버리지를 모을 수 없다.**
- **DuckStation은 플레이는 되지만 메모리·BP가 없다.**
- **PCSX-Redux만 플레이 가능 + 계측 가능**이다. 설치: `D:\pcsx-redux` (GPL-2.0).
  실행 `pcsx-redux.exe -iso D:\srw4s_ko\game.cue -run` — **경로에 공백/괄호가 있으면 인자가 깨져**
  OpenBIOS 큐브만 돈다(공백 없는 cue를 따로 뒀다).

남은 선행 작업: Redux Lua API 확인(설치본에 .lua 없음, 문서 사이트 403, 저장소에 docs/ 없음 —
API는 `src/lua/`에 있다). 확인되면 `0x80110594` 훅으로 (뱅크,슬롯)을 파일에 적는 스크립트를 만든다.

### 이 추적이 증명하는 것 / 못 하는 것
플레이한 만큼만 덮으므로 **완전성은 증명하지 못한다.** 목적은 표본으로 closure 모델을
검증하는 것이다 — 히트한 슬롯 중 closure(1,624) 밖 비율이 낮으면 정적 추정을 믿고
closure 우선 번역으로 가고, 높으면 전량 번역이 필요하다는 뜻이다.

## 공간 판정 — 재뱅킹이 필요하다

| 뱅크 | 레코드 | closure | 정본B | 번역대상B | 한글 1.30x | 증가 |
|---:|---:|---:|---:|---:|---:|---:|
| 0 | 1552 | 241 | 63,479 | 58,869 | 76,529 | +17,660 |
| 1 | 1410 | 257 | 63,583 | 60,444 | 78,577 | +18,133 |
| 2 | 1293 | 305 | **65,273** | 61,909 | 80,481 | +18,572 |
| 3 | 959 | 96 | 48,062 | 40,671 | 52,872 | +12,201 |
| 4 | 1442 | 276 | 64,396 | 60,702 | 78,912 | +18,210 |
| 5 | 561 | 0 | 64,947 | 62,551 | 81,316 | +18,765 |
| 6 | 1466 | 311 | 61,127 | 56,710 | 73,723 | +17,013 |
| 7 | 387 | 100 | 16,648 | 13,870 | 18,031 | +4,161 |

전량 +124,715 B(창 1.90개분) / closure만 +18,771 B(창 0.29개분).

**뱅크가 이미 꽉 찼다** — 뱅크2는 65,273/65,536으로 여유 263 B다. 따라서 closure만 번역해도
제자리 증량은 불가능하고 **재뱅킹**이 필요하다.

가능한 이유: 접근자가 `base = header[bank] & 0xFFFF0000`로 뱅크 베이스를 만든다
(`0x4DD20` `lw $a2,($v0)` / `0x4DD24` `3C02FFFF` / `0x4DD28` `00C23024` — 실측 확인).
헤더 61칸 중 **5칸이 비어 있고**, 파일은 RAM 상주가 아니라 디스크 스트리밍이라 늘릴 수 있다.

### 재뱅킹 설계
1. 파일 끝에 새 64KiB 창을 붙인다(전량이면 2개, closure면 1개로 충분)
2. 넘치는 뱅크의 **테이블 + 그 레코드들**을 새 창으로 옮긴다(테이블 단위로 옮겨야 u16이 성립)
3. 헤더 엔트리를 새 테이블 오프셋으로 갱신
4. 디스크에서 파일이 커지므로 섹터 재배치 필요 -> `tools/patch_image_reloc.py`

### 반드시 먼저 통과시킬 게이트
**무번역 항등 왕복** — 번역을 하나도 넣지 않고 재삽입해 원본과 SHA-256이 같아야 한다.
D_NAMES에서 이 게이트가 없어 순서·인접성 파괴를 실기에서야 발견했다.

## 번역 단위 재설계 + 왕복 게이트 (2026-08-23)

### 스팬 모델은 대사에 맞지 않는다
처음엔 D_NAMES처럼 제어 토큰마다 끊어 스팬을 만들었는데, 대사는 **문장 중간에 줄바꿈(F6)** 이
들어가서 `ません」`, `甲児「そういや,` 같은 **번역 불가능한 조각**이 나왔다. 어순이 다른
한국어는 조각 단위로 옮길 수 없다.

그래서 **번역 단위 = 레코드**로 바꾸고 제어 토큰을 인라인 표식으로 보존한다:
```
{N} 줄바꿈 F6 · {P} 페이지 F7 · {A} FA
{8:xx} {9:xx} {E:xx}   1바이트 인수
{B:xxxx} {C:xxxx} {D:xxxx}  2바이트 인수
{G:xxx} 글리프 ID 직접 지정
```
역문은 원문과 **같은 표식을 같은 개수로** 가져야 한다.

### 문자표는 단사가 아니다 (왕복 게이트가 잡아냄)
`tools/verify_mb_roundtrip.py`가 129건 불일치를 잡았고 원인이 둘이었다:
1. **같은 글자에 글리프 ID가 둘** — `父`=3D9/3E6, `避`=172/5BE, `塔`=44A/4BE, `兜`=100/44B 등 15종.
   인코더가 낮은 ID를 고르면 원본과 달라진다.
2. **여러 글자로 풀리는 글리프** — `HP`가 글리프 하나(`0x0EE`)다. 재인코딩하면 H+P 둘이 되어
   길이가 변한다.

`{G:xxx}` 이스케이프로 해결했고 지금은 **9,070/9,070 왕복 일치**다.

> D_NAMES는 스팬 밖 바이트를 그대로 복사하는 방식이라 이 함정을 피해 갔지만,
> 레코드를 통째로 재인코딩하는 M_BANKS에서는 그대로 터졌을 문제다.
> **왕복 게이트를 먼저 세우지 않았다면 번역을 다 하고 나서 발견했을 것이다.**

## 재삽입 제약과 재뱅킹 설계 (2026-08-23)

### 제자리 증량은 불가능하다
1단계 재삽입기(재뱅킹 없음)를 만들었더니 뱅크0에서 바로 막혔다:
**필요 63,479 B > 가용 60,684 B** — 역문을 하나도 안 넣은 상태에서도 넘친다.

원인: **정본 레코드끼리도 겹친다.** 토큰 정렬이 다른 지점에서 시작하는 레코드가 다른 레코드
안에 박혀 있어, 겹침 없이 나란히 늘어놓으면 원본이 쓰던 공간보다 더 든다.
(물량 산정에서 겪은 중복 계산 함정이 배치에서도 그대로 나타났다.)

### 재뱅킹이 답이고, 단위는 '테이블'이다
포인터가 **뱅크 상대 u16**이므로 테이블과 그 레코드는 같은 64KiB 창에 있어야 한다.
따라서 재배치 단위는 `테이블 1개 + 그 테이블이 참조하는 모든 레코드`다.
공유 레코드(전체의 8%)는 창마다 복제한다 — 읽기 전용이라 안전하다.

실측 (표 56개):

| | 값 |
|---|---:|
| 테이블 단위 합계 (표+레코드, 복제 포함) | 592,920 B |
| 가장 큰 단위 | 39,086 B |
| 한글 1.30배 적용 시 최대 단위 | **50,811 B** (한도 65,536) |
| 전량 한글 시 총량 | 770,796 B (현재 493,209 B) |

**모든 단위가 한글화 후에도 64KiB 안에 들어간다.** 창당 3~4단위씩 담으면 약 14창.
디스크에서는 파일이 +278 KB 커지므로 섹터 재배치가 필요하다(`tools/patch_image_reloc.py`).

헤더는 61칸 중 56칸 사용 — 창을 늘려도 **엔트리 수는 그대로**이고 값만 새 오프셋으로 바뀐다.

## 재뱅킹 재삽입기 + 항등 게이트 통과 (2026-08-23)

`tools/mb_rebank.py` — 테이블 단위(테이블 + 그 테이블이 참조하는 모든 레코드)를 64KiB 창에
first-fit으로 담는다. 공유 레코드는 창마다 복제한다(읽기 전용이라 안전).

무번역 항등 빌드 결과:
```
단위 56개 -> 창 10개
크기 493,209 -> 661,577 B   (증가분은 공유 레코드 복제)
슬롯 14,336 중 바이트 일치 14,105 / 불일치 0 / 새로 생긴 종단 실패 0
원본부터 죽은 슬롯 231 (118은 원본·새것 둘 다, 113은 원본만 — 새 배치에서 오히려 정상화)
```

`tools/verify_mb_rebank.py`가 게이트다. **회귀만 실패로 센다** — 원본에서 이미 종단하지 않는
슬롯은 내 책임이 아니므로 분리해 집계한다. 이 구분을 안 하면 231건이 전부 실패로 보여
멀쩡한 빌드를 잘못 버리게 된다.

### 별칭 처리 규약
접미사 공유 별칭은 역문이 없으면 부모 안 상대 위치를 그대로 쓰고, **역문이 있으면 접미사
위치가 달라지므로 원문 바이트로 따로 배치**한다. 번역된 레코드의 별칭은 일본어로 남는다 —
정확성을 위한 의도적 선택이며, 개선하려면 별칭별 역문이 따로 필요하다.

   지금 D_NAMES용 할당표에는 M_BANKS에서 새로 나온 음절(`녀`·`씨`·`딸` 등)이 없다.
2. **디스크 반영** — 재뱅킹으로 파일이 493KB -> 662KB(무번역 기준). 섹터 재배치 필요.
3. D_NAMES 빌드의 프리즈 확인(정신 메뉴·스테이지 2) — 미해결이면 플레이가 막힌다.

## 재뱅킹 최종형 (2026-08-23)

창 하나 = 64KiB. 창 안 구조는 `[이 창에 든 표들(각 0x200)][공유 풀]`이고,
**창0만 헤더(244 B) 뒤에서 시작**한다(베이스는 0). 창0을 64KiB 경계로 밀면 그만큼이 통째로 죽는다.

풀은 D_NAMES와 같은 토큰 검증 방식이다. 후보 위치를 **이미 배치된 레코드의 토큰 시작점**으로만
제한하고, 긴 레코드부터 넣어 짧은 접미사가 흡수될 기회를 남긴다. 별칭은 따로 다루지 않는다 —
자기 바이트열(별칭 시작~종단)을 그냥 대상으로 넣으면 부모가 미번역인 경우 접미 공유가 알아서
부모 안쪽을 가리킨다. 부모가 번역된 별칭만 원문 바이트로 남는다.

창 채우기는 원래 뱅크 순서로 훑되, **안 들어가는 단위가 나와도 창을 닫지 않고** 남은 단위 중
들어가는 것을 계속 채운다(닫으면 창이 비어 남는다).

| 조치 | 항등 크기 |
|---|---:|
| 단순 재배치 | 664,124 B |
| + 창 단위 공유 풀 | 647,165 B |
| + 창0 회수 | **527,578 B** |
| 원본 | 493,209 B |

역문 385레코드 반영 시 547,665 B = 268섹터(원본 241). 디스크는 `M_FIELD`·`SC_00`을
트랙1 꼬리로 옮겨 자리를 냈다. **꼬리 잔여 111섹터**가 앞으로의 증량 예산이다.

## 재뱅킹은 왜 깨지는가 — 4단 이분 탐색 (2026-08-24)

| 시험 | 디스크 | 결과 |
|---|---|---|
| M_FIELD·SC_00 만 트랙1 꼬리로 재배치 | M_BANKS 원본 | **통과** |
| 크기만 키움 (원본 뒤에 0 패딩, 241 -> 258섹터) | 내용 한 바이트도 안 바꿈 | **통과** |
| 제자리 치환 (역문 20개, 길이 정확히 보존) | 크기 동일 | **통과** |
| 항등 재뱅킹 (번역 0개, 배치만 재구성) | 258섹터 | **실패** — 대사창에 뜻 없는 글자, 정지 |

무죄가 확정된 것: 파일 재배치 / 파일 크기 증가 / 내용 치환.
남는 원인: **배치 재구성 자체**.

### 런타임 주소 계산은 내 모델과 같다 (디스어셈블 확인)

MAP 오버레이 `0x80154090`:
```
a2 = header[bank] & 0xFFFF0000        ; 뱅크 베이스
v0 = tablecache[bank*0x200 + slot*2]  ; u16, 부팅 때 61표 전부 RAM 캐시
read(file=18, dest=sp+16, offset = a2 + v0, len = 0x400)
```
항등 재뱅킹 산출물은 **14,105 슬롯 전부 바이트 일치**인데도 실기에서 깨진다.
따라서 런타임은 (뱅크,슬롯) 외에 **레코드 뒤에 오는 바이트에도 의존**한다
(0x400 창을 이어 읽는 것으로 보인다). D_NAMES S00/S01/S02 조각과 같은 구조다.

배제한 가설: 표가 섹터 경계를 넘음(원본 17개 / 재뱅킹 2개), `offset & 0x7FF > 0x400`
(원본 7,307슬롯), 읽기 루틴의 크기·오프셋 상한(없음), 레코드 안 내장 포인터(FB/FC/FD 피연산자가
같은 뱅크 레코드 시작과 일치하는 비율 3~17%, 우연 범위).

## 재뱅킹 v2/v3 — 이어읽기 보존과 뱅크 한도 (2026-08-24)

### v2: 구간 단위 이동

이동 단위를 레코드에서 **구간(run)** 으로 바꿨다. 표가 읽을 수 있는 `[포인터, 포인터+reach)`
를 모아 겹치는 것끼리 합친 원본 연속 구간을 통째로 옮긴다.
`tools/mb_rebank2.py` / 검증 `tools/verify_mb_rebank2.py`(이어읽기까지 대조).

| reach | 크기 | 섹터 | 실기 |
|---|---:|---:|---|
| 0x400 | 752,417 B | 368 | 공간 부족으로 미시험 |
| 0x200 | 633,122 B | 310 | **실패** — 스테이지 2 정지 |
| 0x100 | 587,294 B | 287 | 미시험 |

=> 엔진은 포인터 뒤 **0x400 을 실제로 쓴다**. 보존폭을 줄이는 길은 막혔다.

### 포장 실험

"구간이 많이 겹치는 표끼리 묶기"(한계 비용 최소)를 시험했으나 구간이 파편화돼
**오히려 커졌다**(0x400 기준 752,417 -> 821,132 B). 원래 뱅크 순서로 채우는 게 가장 촘촘하다.

### v3(`rel*2` 훅) — 폐기

뱅크 한도를 128KiB 로 늘리려 포인터를 `rel*2` 로 읽게 고쳤으나,
**원본 포인터 대상의 44%(14,285회 중 6,280회)가 홀수 오프셋**이라 절반이 주소지정 불가다.
`tools/mb_rebank3.py` 는 그 사실을 발견한 자리에서 실패한다. 남겨 두되 쓰지 않는다.

### v4 설계 — 마스크 제거

```
현재: base = header[bank] & 0xFFFF0000
변경: base = header[bank]
```
명령 두 줄(`lui $v0,0xFFFF` / `and $a2,$a2,$v0`)을 `nop` 으로 바꾸는 게 전부다.
창이 64KiB 경계에 묶이지 않아 **표를 미끄러뜨리며 구간을 공유**할 수 있다.

reach 0x400 으로 전역 병합하면 구간이 **8개, 487,536 B** 뿐이다.

| 항목 | 크기 | 섹터 |
|---|---:|---:|
| 전역 구간 8개 + 표 56개 + 헤더 | 516,452 B | 253 |
| 확보 가능(앞뒤 파일 재배치) | 649,216 B | 317 |
| **번역용 여유** | **132,764 B** | **64** |

남은 문제: 56개 표 중 13개가 두 개 이상의 구간을 참조하고, 그중 6개는 참조 범위가
64KiB 를 넘는다(최대 65,528 B, 한도는 65,535 - 0x200 = 65,023).
구간 배치 순서를 바꾸거나 먼 구간을 복제해 풀어야 한다.

## v4 — 동작 확인된 구성 (2026-08-24)
