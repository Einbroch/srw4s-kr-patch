기준일: 2026-08-22  
상태: **정적 계약 확정 / 런타임 확인 항목 남음**

번역문은 원문보다 길어진다. 이 문서는 "얼마나 길어지는가"와 "그 길이를 어디에 어떻게 넣는가"를
증거로 확정한 것만 적는다. 추정과 미확인은 그렇게 표시한다.

> **2026-08-23 정정** — 아래 §1의 1.575배는 **이름 레코드**의 배율이다. S00/S01/S02는 산문이
> 아니라 창 그리기 스크립트라 바이트의 22~49%만 번역 대상이고, span 배율은 1.28–1.39배다.

## 1. 얼마나 길어지는가 (실측)

추정 대신 도너(컴플리트 박스 한국어 패치)의 **실제 한국어 번역**을 우리 `D_NAMES`의 일본어 파생
보기에 매칭해 인코딩 크기를 쟀다. 재현: `tools/measure_growth.py`.

- 고유 레코드 2,653개 중 **881개(33.2%)** 가 도너 번역과 매칭됐다.
- 매칭 구간 실측: **5,545 B → 8,734 B = 1.575배 (+57.5%)**

증가의 원인은 인코딩 비대칭이다. 가타카나는 이 엔진에서 **1바이트/글자**인데 한글 음절은
**2바이트**다. 그래서 기체·무기·파일럿 이름처럼 가나가 많은 구간이 가장 크게 는다.

| 구간 | 실측 비율 | 매칭 표본(B) | 메모 |
|---|---:|---:|---|
| S07 파일럿 약칭 | 1.698 | 527 | 가나 100% |
| S06 파일럿 풀네임 | 1.654 | 1,054 | |
| S11 지형 | 1.604 | 255 | |
| S04 유닛명 | 1.593 | 732 | |
| S08 무기명 | 1.566 | 2,121 | 최대 표본 |
| S13 상태/적응 | 1.367 | 491 | 한자 비중 |
| S00/S01/S02/S17 산문 | 1.2–1.9 | 15–62 | **표본이 너무 작아 신뢰 못 함** |

섹션별 비율을 적용한 투영은 `D_NAMES` 전체 **72 + 8,180(포인터표) + 약 66,000(문자열) ≈ 74,000 B**다.
다만 문자열 41,967 B 중 약 29,000 B가 산문 4개 섹션(S00/S01/S02/S17)이고 그 비율의 표본이
15~62 B뿐이므로 **이 투영의 오차 범위는 크다**. 확정 수치는 승인된 한국어 코퍼스에서 다시 낸다.

확정적으로 말할 수 있는 것: **현재 `D_NAMES`가 STAYDAT에서 차지한 슬롯(다음 슬라이스까지 53,248 B)
안에는 번역본이 들어가지 않는다.**

## 2. 어디에 넣는가 — D_NAMES는 이미 64KiB 뱅킹을 지원한다

MAP 해제물 `0x4E4A8`(RAM `0x80154828`)의 접근자가 D_NAMES 주소를 만드는 규칙이다.

```mips
lui  $a2, 0x8016
lw   $a2, -0xcf0($a2)      ; a2 = D_NAMES base  (전역 0x8015F310)
sll  $a0, $a0, 2
addu $a0, $a0, $a2
lw   $v1, ($a0)            ; v1 = header[section]  (u32)
addu $a0, $v1, $a2         ; 포인터표 주소 = base + header
lui  $v0, 0xffff
and  $v1, $v1, $v0         ; header & 0xFFFF0000
addu $v1, $v1, $a2         ; 문자열 베이스 = base + (header & 0xFFFF0000)
sll  $a1, $a1, 1
addu $a1, $a1, $a0
lhu  $v0, ($a1)            ; u16 포인터
jr   $ra
addu $v0, $v1, $v0         ; 반환 = 문자열 베이스 + u16
```

즉 **섹션마다 64KiB 창을 따로 가질 수 있다.** 지금은 18개 헤더 값이 모두 `< 0x10000`이라
`& 0xFFFF0000`이 0이 되어 한 창에 몰려 있을 뿐이다. 헤더는 u32이므로 섹션 k의 헤더를
`0x00013456`처럼 주면 그 섹션의 표는 `base+0x13456`, 문자열은 `base+0x10000+u16`으로 풀린다.

따라서 **포인터 폭 확장이나 엔진 패치 없이** D_NAMES를 여러 64KiB 창으로 재배치할 수 있다.
제약은 다음 셋뿐이다.

1. 한 섹션의 포인터표와 그 섹션의 모든 문자열은 **같은 64KiB 창** 안에 있어야 한다.
2. 다른 섹션의 표 안쪽을 가리키는 별칭 섹션(S05·S09·S10·S16)은 호스트 섹션과 **같은 창**에 둔다.
3. 전체 blob이 RAM에 들어가야 한다.

> **2026-08-23 런타임 검증으로 정정** — 위 뱅킹은 **MAP 오버레이에만** 해당한다.
> BATTLE 오버레이의 D_NAMES 접근자(RAM `0x80146EC4`, BATTLE.dec 파일 `0x40B44`)에는
> `& 0xFFFF0000`이 **없다**. `base + u16`으로 평탄하게 푼다.
>
> ```mips
> lui  $v1, 0x8016
> lw   $v1, 0x3b74($v1)   ; base (전역 0x80163B74 = BATTLE 안의 베이스 표 사본)
> sll  $a0, $a0, 2
> addu $a0, $a0, $v1
> lw   $v0, ($a0)         ; header[section]
> sll  $a1, $a1, 1
> addu $v0, $v1, $v0      ; 표 = base + header   (마스킹 없음)
> addu $a1, $a1, $v0
> lhu  $v0, ($a1)
> jr   $ra
> addu $v0, $v0, $v1      ; 반환 = base + u16    (단일 64KiB 창)
> ```
>
> 따라서 실제 상한은 **D_NAMES 전체 ≤ 65,536 B**다(전투 화면이 파일럿·기체·무기명을 읽으므로
> BATTLE 경로는 살아 있다). 뱅킹을 쓰려면 BATTLE의 이 접근자에 MAP과 같은 마스킹을 넣는
> **ASM 개입이 필수**다. 두 오버레이가 같은 데이터를 다른 규약으로 읽는다는 것이
> 이 게이트에서 가장 비싼 발견이다.

같은 파일의 다른 blob은 규약이 다르다. 예로 `D_OBJCT` 접근자(RAM `0x801547F0`)는
`& 0xFFFF0000`이 없고 **표 상대** 포인터를 쓴다. blob마다 접근자를 확인하고 옮겨야 한다.

### 베이스 재배치 방법

각 상주 blob의 RAM 주소는 MAP 해제물 `0x58F68`부터의 **포인터 표**에 들어 있다
(RAM `0x8015F2E8`~). D_NAMES 슬롯은 MAP 파일 오프셋 `0x58F90`(RAM `0x8015F310`), 현재 값
`0x80069800`. MAP 안에서 이 슬롯을 읽는 곳은 위 접근자 **한 곳뿐**이다.

같은 표의 사본이 `BATTLE.dec` `0x5D7F4`에도 있다(값 동일). **BATTLE 쪽 소비자는 아직 특정하지
못했다** — BATTLE에는 `& 0xFFFF0000` 뱅킹 시그니처가 없다. 재배치 전에 반드시 확인한다.

같은 표에서 확인된 다른 슬롯: `0x8015F304` = `0x80056800`(주 글꼴 디스크립터, `FONT.md`와 일치),
`0x8015F2EC` = `0x80020000`(STAYDAT).

| 항목 | 값 | 재삽입 시 의미 |
|---|---:|---|
| 포인터 엔트리 | 4,090 | |
| 고유 대상 | 2,653 | |
| **공유 대상** | **566** (최다 192회) | 한 번역이 여러 자리에 나온다. 분리하면 공간이 는다 |
| **레코드 안쪽 앵커** | **13** | 포인터가 다른 레코드의 +2/+4/+5를 가리킨다 |

안쪽 앵커 13개는 전부 S13/S16의 인접 레코드 쌍이다(예: 레코드 `0xB199..0xB1A2`를 S13:E232가,
그 `+2` 지점을 S13:E264가 가리킨다). 도너 프로젝트가 같은 계열에서 겪은 사고와 같은 모양이다
(`reference/srwcb-korean-patch/docs/RELEASE_NOTES_v0.11.34.md`, v0.11.35: "레코드 **안쪽**을
겨누는 앵커", 개조 확정 시 프리즈). **재배치기는 레코드 시작만이 아니라 이 13개 내부 오프셋도
같이 옮겨야 한다.**

덮이지 않은 3,841 B는 대부분 `FF FF`로 시작해 실제 텍스트가 이어지는 조각이다. 도너가
"잎 노드가 안 가리키는데도 게임이 읽는 **비참조 레코드**"를 세 게임 합쳐 160곳 발견한 것과
같은 모양이다(v0.11.30). **회수 가능한 여유로 계산하지 않는다.**

## 4. M_BANKS — 같은 뱅킹, 파일은 자유롭게 커질 수 있다

- 파일 493,209 B = 물리 64KiB 창 **8개**, non-null 뱅크 **56**개, 런타임 슬롯 **14,336**개.
- 소비자는 `(header[bank] & 0xFFFF0000) + u16` 위치부터 **정확히 `0x400` B**를 읽는다.
  실측 최장 레코드 **1,023 B**로, 0x400 창을 넘는 레코드는 **0개**다. 즉 1,023 B가 설계 상한이다.

|---:|---:|---:|---:|
| 0 | 9 | 63,154 | 2,382 |
| 1 | 6 | 64,069 | 1,467 |
| 2 | 6 | 64,253 | 1,283 |
| 3 | 12 | 51,444 | 14,092 |

## 5. 디스크 예산

- Track 1은 166,731 섹터, 마지막 파일(`/STR/PROLOG.STR`)이 LBA 166,581에서 끝난다.
  **꼬리 여유 150 섹터 = 307,200 B.** 파일 사이 빈틈은 0이다.
- `NULL.DA`(27 MB)와 `CMSONG.DA`는 LBA 166,881 / 181,881로 **오디오 트랙(2·3) 영역**에 있다.
  도너는 같은 모양의 트레일링 null 영역을 썼지만 그 디스크는 전체를 단일 데이터 트랙으로
  선언해야 했다. 이 디스크의 트랙 2·3은 실제 CD-DA 음악이므로 같은 방법을 그대로 쓸 수 없다.
- 이 cue는 트랙마다 **파일이 분리**돼 있다(Track 1/2/3 각각 .bin). 따라서 Track 1 뒤에 섹터를
  덧붙여도 오디오 파일 자체는 건드리지 않는다. 다만 ISO 안의 `CMSONG.DA`/`NULL.DA` LBA와
  볼륨 크기, cue의 트랙 시작 위치를 함께 갱신해야 한다. **아직 증명하지 않았다.**

예상 증가분(투영): M_BANKS 약 +250 KB(122섹터), D_NAMES 재배치분 약 +25~75 KB(13~37섹터).
150섹터 여유로는 부족하므로 **Track 1 확장 경로를 별도 게이트로 증명해야 한다.**

## 6. 남은 확인 항목 (런타임 증거 필요)

1. **BATTLE의 D_NAMES 소비 규약** — BATTLE에도 베이스 표 사본이 있으나 뱅킹 시그니처가 없다.
   두 오버레이가 다른 규약을 쓰면 재배치가 한쪽에서만 맞는다.
2. **STAYDAT 뒤 RAM이 실제로 비어 있는가** — 현재 STAYDAT는 `0x80020000`~`0x8009C167`.
   재배치 대상 창을 그 뒤에 두려면 `0x8009C168` 위쪽이 다른 용도로 안 쓰이는지 확인해야 한다.
   (주의: `0x80080800/0x80081000/0x80081800`은 SC_01–03 stage 창이 **STAYDAT 영역 안으로**
   덮어쓰는 자리다. 같은 함정이 위쪽에도 있을 수 있다.)
3. **게임이 D_NAMES 영역에 쓰기를 하는가** — 주인공 이름은 플레이어가 입력한다. 그 문자열이
   D_NAMES 레코드 자리에 기록된다면 재배치가 그 쓰기 주소도 따라가야 한다.
4. **재압축 LZB의 런타임 소비** — MAP/BATTLE을 수정하면 재압축본을 게임이 실제로 풀어 쓰는지
   확인해야 한다(현재는 해제·재압축 왕복만 증명됨).

이 넷은 메모리 읽기/쓰기 감시가 필요해 DuckStation으로는 얻을 수 없다. emucap Mednafen 어댑터를
이 호스트에 세우는 작업과 묶는다.

## 7. 재배치 설계 초안 (창 배치)

별칭 섹션은 호스트 섹션의 **표 안쪽**을 가리키므로 반드시 같은 창에 둔다.

| 그룹 | 구성 | 별칭 관계 |
|---|---|---|
| A | S04 + S05 | S05 = S04 표 `+512 B` |
| B | S08 + S09 + S10 | S09 = S08 표 `+512 B`, S10 = S08 표 `+1024 B` |
| C | S13 + S16 | S16 = S13 표 `+448 B` |

현재 섹션별 고유 문자열 바이트(별칭은 호스트 풀을 공유):

```
S00 12,021   S01 9,655   S02 5,174   S04 1,885   S06 2,133   S07 1,083
S08 4,142    S11   264   S12   468   S13 1,820   S14   586   S15   688   S17 2,048
```

1.575배 투영에서 산문 3개(S00·S01·S02)만 약 40 KB, 나머지 전부가 약 25 KB다. 포인터표 8,180 B를
더해도 **64 KiB 창 2개면 충분하다.**

- 창 0: S00 + S01 + S02 (+ 각 표)
- 창 1: 나머지 전 섹션 (+ 각 표)

이 배치면 blob 전체 크기는 `0x10000 + (창 1 사용분)` ≈ 90 KB 수준이고, 현재 52 KB 대비
RAM 증가는 약 38 KB다. 창 0에 여유를 더 두려면 S02를 창 1로 옮기는 변형도 가능하다.

재배치기가 반드시 지켜야 할 불변식:

1. 별칭 그룹은 같은 창, 그리고 별칭의 표 시작 오프셋 차이(`+448/+512/+1024`)를 그대로 유지한다.
2. §3의 **레코드 안쪽 앵커 13개**는 레코드 시작과 함께 내부 오프셋도 재계산해 옮긴다.
3. 공유 대상 566개는 기본적으로 공유를 유지한다(분리는 공간을 늘린다).
4. 덮이지 않은 3,841 B 조각은 원위치 그대로 옮기고 회수하지 않는다(비참조 레코드 가능성).
5. 헤더 u32 = `(창 인덱스 << 16) | 창 안 표 오프셋`.
