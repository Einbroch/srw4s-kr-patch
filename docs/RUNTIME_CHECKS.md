# 런타임 확인 4건 — 결과

기준일: 2026-08-23  
환경: emucap Mednafen 어댑터(이 호스트에 새로 빌드), PoC 이미지, 1화 맵/전투까지 진행.

## 0. 먼저 — 브레이크포인트 보정 (이걸 안 하면 전부 거짓 음성)

**`write` 브레이크포인트를 `memory_type: "ram"`(물리 오프셋)으로 걸면 한 번도 발화하지 않는다.**
`memory_type: "cpu"` + KSEG0 주소(`0x80xxxxxx`)로 걸어야 발화한다.

보정 실험: 스택 영역(매 프레임 쓰기가 확실한 곳)에
- `ram` `0x1F0000–0x1FFFFF` → 10프레임에 이벤트 **0건**
- `cpu` `0x801F0000–0x801FFFFF` → 10프레임에 이벤트 **4,096건**(상한)

`read_memory`/`find_pattern`은 `ram`(물리)이 정상 동작한다. **BP만 규약이 다르다.**
이 보정 전에 얻은 "쓰기 없음" 결과는 전부 폐기했다.

또 하나: `poll_events` 큐는 FIFO에 잔여가 남는다. BP를 갈아끼운 뒤에는 `count`가 0이 될 때까지
먼저 드레인하고 나서 새로 실행해야 이전 BP의 이벤트를 오독하지 않는다.

## 1. BATTLE의 D_NAMES 소비 규약 — **해결 (정정 발생)**

먼저 런타임에서 **MAP 오버레이가 RAM `0x80106380`에 적재됨**을 확정했다.
`find_pattern`으로 `MAP.dec[0:16]`을 찾으면 RAM 오프셋 `0x106380` 단 한 곳에 매칭되고,
`MAP.dec[0x30000:+128]`과 RAM `0x80136380`의 128바이트가 **완전히 일치**한다.

전투가 시작되면 같은 주소 `0x106380`에서 `BATTLE.dec[0:16]`이 매칭된다.
즉 **BATTLE.LZB는 MAP과 같은 자리에 교체 적재**된다. 따라서 BATTLE 안의 베이스 표 사본
(BATTLE.dec 파일 `0x5D7F4`)은 런타임 주소 `0x80163B74`다.

이 주소를 읽는 코드를 찾으니 접근자가 하나 있다 — RAM `0x80146EC4`(파일 `0x40B44`).
**MAP과 달리 `& 0xFFFF0000` 마스킹이 없다.** 문자열을 `base + u16`으로 평탄하게 푼다.

| | MAP (`0x80154828`) | BATTLE (`0x80146EC4`) |
|---|---|---|
| 표 주소 | `base + header[sec]` | `base + header[sec]` |
| 문자열 베이스 | `base + (header[sec] & 0xFFFF0000)` | `base` |
| 창 | 섹션별 64KiB 뱅킹 | **단일 64KiB 평탄** |

**결론**: `D_NAMES` 전체는 **65,536 B 이하**여야 한다. 뱅킹으로 넓히려면 BATTLE의 이 접근자에
MAP과 같은 마스킹을 넣는 ASM 개입이 필수다. `REINSERTION.md` §2의 "엔진 패치 없이 뱅킹 가능"은
MAP만 본 결론이었고 이걸로 정정한다.

## 2. STAYDAT 뒤 RAM이 비어 있는가 — **2026-08-23 정정: 비어 있지 않다**

> 아래에서 "`0x80166000–0x80189FFF`가 4,800프레임 동안 쓰기 0건"이라 했던 것은 **스테이지 단계만 본
> 표본 오류**다. 그 구간 전체가 게임의 작업 힙(`0x80161508`+310,312 B)이고 MAP 초기화마다 통째로
> 0으로 지워진다. 근거와 정정은 `LOADER_HOOK.md` §3(b).

## 2. (원래 기록) STAYDAT 뒤 RAM이 비어 있는가

- STAYDAT는 `0x80020000–0x8009C167`. 그 **바로 위는 비어 있지 않다** —
  `0x800A0000`, `0x800A8000`에 실사용 데이터가 있다.
- 오버레이(MAP/BATTLE)는 `0x80106380`부터. BATTLE(388,880 B)이 `0x80165550`까지 쓴다.
- 오버레이 위 구간 `0x80166000–0x801AFFFF`를 write BP로 감시하니 600프레임에 4,096건(상한).
  주소 분포는 `0x8018A284` 1점과 **`0x801A4000–0x801A87BE`** 집중이었다.
- 그래서 **`0x80166000–0x80189FFF`(144 KiB)** 로 좁혀 다시 감시했다.
  맵·대사·유닛 상태·전투 애니메이션을 포함한 **4,800프레임 동안 쓰기 0건**.

**결론**: D_NAMES 재배치 후보는 `0x80166000–0x80189FFF`다. 단 이건 1화 한 장면의 관측이므로
인터미션·다른 시나리오·전투 연출 종류를 더 돌려 확인해야 한다. **아직 "비어 있다"로 확정하지 않는다.**

## 3. 게임이 D_NAMES에 쓰는가 — **해결 (쓰기 없음)**

`cpu` write BP를 `0x80069800–0x80076287`(D_NAMES 전 구간)에 걸고
주인공 설정 → 월드맵 → 시나리오 대사 → 유닛 상태 화면 → 맵 메뉴 → 턴 종료 → 적 페이즈 →
전투 애니메이션까지 **4,800프레임 이상** 돌렸다. **쓰기 이벤트 0건.**

같은 실행에서 `0x80166000–0x80189FFF` BP도 0건이었고, 보정 실험이 BP가 살아 있음을 증명하므로
이 0건은 "BP가 안 걸렸다"가 아니라 실제 관측이다.

**결론**: D_NAMES는 런타임 읽기 전용으로 보인다. 주인공 이름은 D_NAMES 레코드가 아니라 다른
버퍼에 있다(대사에서 `FB` 셀렉터로 끌어온다). 재배치기가 쓰기 주소를 따라갈 필요는 없다.
다만 이름 입력 화면 자체는 이 구간 감시에 포함되지 않았으므로(설정을 건너뜀) 완전 배제는 아니다.

## 4. 재압축 LZB의 런타임 소비 — **해결 (2026-08-23 BATTLE 패치로 닫힘)**

> BATTLE 접근자 패치 이미지에 **우리 인코더가 만든 `BATTLE.LZB`**가 들어갔고 게임이 그것을
> 읽어 해제해 실행했다(전투 정상 동작). 아래는 그 전에 확보했던 해제기 쪽 증거다.
> 상세: `BATTLE_ACCESSOR_PATCH.md`.

직접 확인(재압축한 `MAP.LZB`를 넣은 이미지로 부팅)은 **아직 못 했다.**
레벨 16으로 압축해도 `156,017 B`로 원본 `155,629 B`(76섹터=155,648 B)를 `+369 B` 넘겨
제자리 교체가 안 되고, ISO 재배치 경로가 아직 없기 때문이다.

대신 강한 간접 증거를 얻었다: **우리 해제기의 출력이 게임 자신의 해제 결과와 바이트 동일**하다.
RAM `0x80106380`의 오버레이가 `MAP.dec`와 헤더 16바이트, 그리고 스트림 중간
`0x30000` 지점의 128바이트까지 일치한다. 포맷 계약이 정확하다는 뜻이다.

남은 것은 "우리 **인코더**가 만든 비트스트림을 게임 해제기가 같은 결과로 푸는가"이고,
이는 ISO 재배치 게이트를 연 뒤 재압축본을 실제로 적재해 확인한다.
