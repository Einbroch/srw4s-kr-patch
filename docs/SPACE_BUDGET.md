# D_NAMES 공간 예산 — 정정된 산정과 디스크 재배치

기준일: 2026-08-23

## 1. 앞선 74 KB 투영은 틀렸다

`REINSERTION.md` §1의 "D_NAMES 전체 약 74,000 B"는 **이름 레코드의 배율(1.575배)을 UI 스크립트
레코드에 그대로 적용**해서 나온 값이다. 실제로 S00/S01은 산문이 아니라 **창 그리기 스크립트**다.

```
-判DK!得DK!判DKー      <- 창 윗변
F判ZKH得SKH判ZKG       <- 중간 행
B劣IKN東IKO得IKO判IKC  <- 구분선
〜判EKA円EKAEEEE?      <- 아랫변
```

이 글리프들은 한자가 아니라 **프레임 타일로 쓰이는 글리프 ID**다(교차 버전 문자표가 한자로
디코딩할 뿐이다). 번역 대상은 커서 위치 토큰(`FC`/`FD`) 뒤에 붙는 라벨뿐이다.

도너도 같은 모델을 쓴다 — `second_ui_scripts_overlay.json`은 레코드마다
`replacements: [{relative_start, relative_end, japanese_text, korean_text}]`로 **span만** 교체하고
나머지 바이트는 보존한다(`structural_decoration_glyphs_preserved: true`,
`kana_name_entry_grids_preserved: true`).

## 2. 실측한 두 배율

| 대상 | 표본 | 배율 |
|---|---|---|
| 이름·용어 레코드(레코드 전체가 텍스트) | 도너 매칭 881건 / 5,545 B | **1.575배** |
| UI·대사 **span** | 도너 치환 span 733건 / 7,564 B | **1.28–1.39배** |

span 배율의 폭은 공백 처리 때문이다. 타깃 low bank(글리프 ID `<0xF0`) 236자에 **반각 공백이
없다** — 공백이 2바이트면 1.39배, low bank에 반각 공백을 넣으면 1.28배가 된다.
(도너에도 `despace_nospace.json` 같은 공백 축약 도구가 있다.)

## 3. span 분류와 정정된 투영

`tools/span_classify.py`가 레코드에서 번역 대상 span만 뽑는다.
  * 위치 토큰(`FC`/`FD`) 뒤의 글리프 런만 후보로 본다.
  * 창 그리기 DSL(`-…ー` `F…G` `B…C` `〜…?` + 대문자 라틴 다수)은 제외한다.
  * 이름 입력 화면의 가나 격자(16자 이상, 한자 없음, 가나 60% 이상)는 제외한다.
  * 위치 토큰이 아예 없는 레코드(이름·용어)는 전체를 텍스트로 본다.

결과: **S00은 바이트의 22.3%, S01은 25.2%, S02는 48.5%만 번역 대상**이다.

| | 총 | 번역 span | 투영 |
|---|---:|---:|---:|
| S00 | 12,255 | 2,737 (22.3%) | 13,322 |
| S01 | 9,878 | 2,491 (25.2%) | 10,849 |
| S02 | 5,251 | 2,546 (48.5%) | 6,244 |
| 이름 계열 전체 | 17,236 | 14,687 | 25,682 |
| **문자열 합계** | **44,620** | | **56,097** |

`D_NAMES` 전체 = 헤더 72 + 포인터표 8,180 + 56,097 = **64,349 B**.

- 16-bit 창 한계 65,536 B 대비 **-1,187 B (여유 1.8%)**
- 현재 STAYDAT 슬롯 53,248 B 대비 **+11,101 B**

즉 **뱅킹은 아마 필요 없다**(한 창에 들어간다). 대신 **약 12 KB의 자리**가 필요하다.
여유가 1.8%뿐이라 확정은 승인된 한국어 코퍼스가 나온 뒤에 한다. BATTLE 접근자 패치는
그 여유가 사라질 경우를 위한 보험으로 유지한다.

## 4. 자리를 어디서 만들 것인가 — 두 갈래가 막혔다

**(A) STAYDAT 안에서 밀기 — 위험.** D_NAMES 뒤 영역(`0x80056288`–`0x8009C168`)을 겨누는
**하드코딩 상수가 65곳**이다(MAP 53, BATTLE 6, EXE 6; 예: `0x8008C000`, `0x8009BBC0`,
`0x8009C134`, `0x8008BC20`, `0x8008AA00`). 베이스 표만 고쳐서는 안 되고, 열거의 완전성도
`jalr`/계산 주소 때문에 보장할 수 없다.

**(B) 독립 `DAT/D_NAMES.BIN`을 키우기 — 소용없다.** 실기로 확인했다.
STAYDAT 사본만 한국어로 패치하고 독립 파일은 원본으로 둔 이미지를 부팅해 RAM `0x800740CD`를
읽으니 **한국어 바이트(`F0 02 F0 03 FF`)** 가 나왔다. 게임이 읽는 것은 **STAYDAT 사본**이고
`DAT/D_NAMES.BIN`은 (적어도 이 경로에서는) 죽은 중복본이다.

남은 갈래는 **로더 훅**이다 — 커진 `D_NAMES`를 검증된 빈 RAM 대역
(`0x80166000–0x80189FFF`, 144 KiB)으로 따로 읽어 들이고 베이스 표 u32 두 개를 그리로 돌린다.
이 경로는 디스크 재배치를 전제로 하고, 그 게이트를 아래에서 열었다.

## 5. 디스크 재배치 게이트 — 통과

`tools/patch_image_reloc.py`. 트랙 1 꼬리 LBA **166,581–166,730의 150섹터**(307,200 B)는
mode 2 / submode 0 / 사용자 데이터 전부 0인 진짜 패딩이다. 여기로 파일을 옮기고 ISO
디렉터리 레코드의 LBA·크기(LE/BE 양쪽)를 갱신한다. 쓰는 섹터는 게임의 다른 데이터 섹터와
같은 규약으로 만든다 — sync + MSF(BCD) 헤더 + subheader `08`(마지막 섹터는 `89`) + EDC/ECC.

검증(`MAP.LZB`로 실시):
1. 재압축한 `MAP.LZB` 156,017 B(원본 155,629, 76섹터 예산 155,648을 +369 초과)를
   LBA 139 → **166,581**로 옮겼다(77섹터, 여유 73섹터 남음).
2. 패치 이미지의 ISO를 다시 걸으니 새 LBA·크기로 보고되고 내용 해시가 일치한다.
3. 실기: 전투↔맵 전환을 반복해 MAP이 새 위치에서 다시 적재됐고, RAM `0x80106380`이
   `MAP.dec`와 헤더 32바이트, 스트림 중간 `0x30000`의 64바이트까지 **바이트 동일**했다.
   게임은 `CdSearchFile`로 파일을 찾으므로 LBA 변경이 자동 반영된다.

증거: `analysis/emulator/PASS_map_relocated.png`, 세이브스테이트
`D:\srw4s_poc\state_map_relocated.mcs`.

이로써 M_BANKS 성장(+약 250 KB)에도 필요한 재배치 경로가 열렸다. 다만 꼬리 여유는 150섹터
(307 KB)뿐이므로 M_BANKS 규모에는 부족하고, 트랙 1 확장은 여전히 별도 게이트다.
